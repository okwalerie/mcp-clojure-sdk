# MCP 2026-07-28

This branch adds the per-request protocol alongside the existing 2025-06-18,
2025-03-26 and 2024-11-05 implementation. It is based on `client-support`.
It does not implement the intervening 2025-11-25 revision.

## Server

Existing tool, resource and prompt registration APIs remain available. Modern
requests carry `:_meta` with `:io.modelcontextprotocol/protocolVersion` and
`:io.modelcontextprotocol/clientCapabilities`; client identity is optional.
`server/discover` returns supported versions and current capabilities without an
initialize handshake. Modern results include `:resultType` and server identity.
Cacheable results currently default to a zero TTL and private scope.

A handler can return `protocol/input-required` with a map of sampling,
elicitation or roots requests and optional opaque state. On the next call it can
read `:inputResponses` and `:requestState` from `protocol/*request*`. The SDK
checks that the current request advertises the required client capabilities.
The application must validate responses and authenticate any state that affects
privileges or side effects. Do not trust client-returned state as authorization.

Modern HTTP uses independent POST requests, mirrored MCP method/version/name
headers, and schema `x-mcp-header` annotations. It creates no modern sessions.
Configure `:allowed-origins` explicitly when starting a browser-accessible server;
an Origin header is rejected unless it is in that set. A server configured with
no allowed origins still accepts non-browser requests without Origin.

`subscriptions/listen` uses a request-scoped stream. Registration notifications
are filtered by the acknowledged subscription; cancellation closes the listener.
Application tool execution may outlive cancellation. Applications doing blocking
or external work must enforce their own worker, queue, deadline and shutdown
budgets. The channel transport allows applications to supply bounded strict IO;
`:id-valid?` can impose an application request-ID limit.

The default stdio reader limits input frames to 512 KiB and output frames to
4 MiB. These are transport bounds, not a complete application resource policy.

## Client

The stdio and HTTP `run!` options accept `:protocol-mode :modern`, `:legacy` or
`:auto` (the default). Auto tries discovery before the existing handshake;
modern requires successful discovery. Subsequent modern calls include fresh
client capabilities on every request. A modern call can process up to eight
multi-round retries using the configured sampling/elicitation handlers and roots.

Use `client/listen!` for modern subscriptions. Legacy `ping!`, resource
subscribe/unsubscribe and logging-level operations are legacy methods and are
rejected by a modern server. Server-initiated modern requests use multi-round
results rather than independent JSON-RPC requests.

## Validation and limits

Run `make format`, `make check` and `make test`. Tests cover modern HTTP client
calls, multi-round results, metadata, header mirroring, schema validation,
request-scoped subscriptions, cancellation, exact integer request IDs and legacy
compatibility. The test fixture namespace
`io.modelcontext.clojure-sdk.conformance-server` starts an HTTP endpoint for the
upstream conformance runner. Set its port as the first argument (default 7989).

The official conformance runner at version 0.2.0-alpha.12 passed the scoped
`server-stateless` checks (28 passed; two dynamic list-mutation checks skipped),
`caching` checks (8/8), and `dns-rebinding-protection` checks (2/2). This is not a full
conformance or tier claim. OAuth, Tasks, complete content-fixture coverage,
progress/log streaming, client conformance and the full multi-round conformance
suite have not been validated here. Do not infer support from a passing subset.
